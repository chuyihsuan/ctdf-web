# CTDF 網站內容上下架操作手冊

文件版本：v1.2<br>
適用日期：2026-10-31<br>
適用系統：第一版無資料庫後台 Demo、初期正式版、GitHub、Vercel Demo／Production<br>
後台網址：`https://ctdf-web.vercel.app/admin/login/`

## 1. 手冊目的與適用範圍

本手冊說明中華民國競技飛鏢總會網站內容的新增、修改、審核、上架、下架與緊急修正流程，讓內容責任與發布權限可以分開，並保留 GitHub 版本、Demo 上板審閱及正式發布紀錄。

目前第一版後台採無資料庫模式：

- 文字、狀態、圖片與附件草稿保存在操作電腦目前瀏覽器的 IndexedDB。
- 後台可預覽、送審、核准並匯出 ZIP 上架包。
- ZIP 是內容交付包，不會自動修改正式網站。
- 副秘書長或技術人員仍須把內容整合至網站、建立 Git 分支與 Pull Request。
- 內容必須先發布至 Demo 環境上板審閱，通過後才可將同一版本發布至正式環境。
- 目前 Demo 尚無一鍵下架功能；下架依本手冊的「下架申請」與 GitHub 流程處理。

## 2. 初期正式版的雙環境發布方式

### 2.1 環境定義

初期正式版應將 Demo 與正式網站分開。正式上線前，技術發布者應完成下列環境設定：

| 環境 | 建議網址 | Git 分支 | 用途 | 可見對象 |
|---|---|---|---|---|
| 後台內容製作 | `https://ctdf-web.vercel.app/admin/login/` 或後續獨立後台網址 | 不直接發布 | 建立草稿、預覽、送審、匯出 ZIP | 授權管理者 |
| Demo／Staging | `https://ctdf-web.vercel.app/` 或獨立 Demo 網址 | `demo` | 完整上板、內部 Review、手機與連結測試 | 總會內部與受邀審閱者 |
| 正式 Production | 測試：`https://ctdf-web-production.vercel.app/`；正式：`https://ctdf.org.tw/`（正式網域啟用後） | `main` | 正式環境測試與對外發布 | 上線前為內部驗收；正式網域啟用後為社會大眾 |

建議由同一個 GitHub repository 連接兩個 Vercel 專案，或使用等效的分支網域設定：Demo 專案只追蹤 `demo`，正式專案只追蹤 `main`。這項設定完成前，不得將 Demo 網址視為正式網站。

第一次使用本手冊前，副秘書長／技術發布者須完成一次性準備：

- [ ] GitHub 已建立 `demo` 與 `main` 分支。
- [ ] 一般內容發布者不能直接推送或強制推送至 `main`。
- [ ] Vercel Demo 專案已連接 `demo`，且固定 Demo 網址可開啟。
- [ ] Vercel Production 專案已連接 `main`，正式網域只指向 Production。
- [ ] GitHub 及 Vercel 的管理權限至少有一位備援管理者。
- [ ] 秘書長知道 Demo 網址與正式網址的差異。
- [ ] 已選定核准紀錄及 ZIP 的保存位置。

### 2.2 初期正式版發布原則

1. 所有新增、修改及一般下架都必須先進入 Demo 環境。
2. Demo Review 通過前，不得合併至 `main`。
3. Demo 通過後，應將「同一個已測試版本」發布至正式環境，不得在中間臨時修改文字、附件或程式。
4. Demo Review 後若有任何修改，即使只改一個字，也須重新部署 Demo 並再次確認。
5. Demo 核准須留下可追溯紀錄，例如 Email、PR 留言或簽核紀錄；口頭同意不得作為唯一依據。
6. 正式發布完成後仍須再次檢查，因網域、快取及正式環境設定可能與 Demo 不同。
7. 僅有個資、法律、資安或重大錯誤等緊急下架，可在秘書長明確授權後先處理正式環境，再補 Demo 與完整紀錄。

### 2.3 分支與發布順序

技術發布者建議採用下列順序：

```text
content/YYYYMMDD-short-title
        ↓ Pull Request／技術檢查
demo 分支
        ↓ Vercel Demo 上板 Review
秘書長或授權主管書面核准
        ↓ 同一 content commit／同一核准版本
main 分支
        ↓ Vercel Production 部署
ctdf.org.tw 正式驗收
```

實務操作時，可先將內容分支合併至 `demo`，通過後再由同一內容分支對 `main` 建立 PR。不要直接把累積多項未核准內容的整個 `demo` 分支合併至 `main`。

## 3. 角色配置

### 3.1 最低必要角色

| 角色 | 建議人員 | 主要責任 | 不負責事項 |
|---|---|---|---|
| 內容管理與核准者 | 秘書長 | 建立或修改內容、檢查資料、預覽、送審、核准、匯出 ZIP、驗收 Demo 與正式網站 | 不直接持有或操作網站部署密鑰 |
| 技術發布者 | 副秘書長或指定技術人員 | 檢查 ZIP、更新網站檔案、建立分支與 PR、部署 Demo、發布及確認正式網站 | 不自行改寫未經核准的內容事實 |

兩人配置是目前 Demo 可運作的最低配置。內容核准與技術發布應由不同人完成，避免單一人員未經覆核直接發布。

### 3.2 視內容加入的角色

| 角色 | 何時需要 | 主要責任 |
|---|---|---|
| 內容提供者／業務承辦 | 賽事、規程、代表隊、影音、會務等專業內容 | 提供原始資料，確認名稱、日期、地點、版本、連結及附件正確 |
| 會長或授權主管 | 重大聲明、政策、爭議事件、對外正式立場、青少年或敏感內容 | 核准是否公開及最終文字，不操作 GitHub |
| 備援技術管理者 | 主要技術發布者無法處理時 | 依相同流程接手發布、回復或緊急下架 |

### 3.3 角色權限原則

1. 內容提供者對資料真實性負責。
2. 秘書長對公開內容、個資、著作權與上架時點負責。
3. 副秘書長／技術人員對版本、部署結果與回復能力負責。
4. 重大或敏感內容須先取得會長或授權主管核准。
5. GitHub、Vercel、網域及密碼管理工具的帳號不得共用一般公開密碼。

## 4. 內容類型與責任分工

| 內容類型 | 原始資料提供者 | 內容核准者 | 上架前重點 |
|---|---|---|---|
| 公告 | 秘書處或業務承辦 | 秘書長；重大公告加會長／授權主管 | 標題、日期、聯絡窗口、附件、有效期限 |
| 賽事 | 賽事承辦 | 秘書長 | 正式賽名、項目、日期、地點、報名網址、規程版本 |
| 影音 | 影音或宣傳承辦 | 秘書長 | 來源網址、縮圖、肖像權、未成年授權、播放狀態 |
| 文件連結 | 文件制定單位 | 秘書長；規章視需要加主管 | 文件版本、發布日期、是否取代舊版、外部連結可開啟性 |
| 固定頁面 | 秘書處 | 秘書長；組織或政策內容加主管 | 組織名稱、聯絡資料、政策文字、最後更新日期 |

## 5. 整體流程與順序

### 5.1 十步流程、角色與介面總表

| 步驟 | 工作 | 主要負責角色 | 使用介面 | 完成結果 |
|---|---|---|---|---|
| 1 | 製作內容並匯出上架包 | 秘書長 | CTDF 後台、瀏覽器 | 已核准 ZIP 上架包 |
| 2 | 技術檢查、建立內容分支及提交 | 副秘書長／技術發布者 | 檔案總管、編輯器、GitHub Desktop | 已推送的內容分支及 commit |
| 3 | 部署至 Demo 環境 | 副秘書長／技術發布者 | GitHub 網頁、Vercel Dashboard | 可供 Review 的固定 Demo 網址 |
| 4 | Demo 上板 Review | 秘書長；必要時加入內容提供者及授權主管 | 瀏覽器、檢核表 | Review 結果及問題清單 |
| 5 | 修正並重新 Review | 秘書長、技術發布者 | CTDF 後台、GitHub Desktop、Demo 網站 | 通過 Review 的核准版本 |
| 6 | 核准發布正式版 | 秘書長；重大內容加授權主管 | Email、GitHub PR 留言或簽核紀錄 | 「同意發布正式版」紀錄及核准 commit |
| 7 | 建立正式版 Pull Request | 副秘書長／技術發布者 | GitHub 網頁 | 以 `main` 為目標的正式 PR |
| 8 | 比對核准版本並合併 | 副秘書長／技術發布者；必要時加第二位覆核者 | GitHub 網頁 | 核准版本已合併至 `main` |
| 9 | 正式部署及技術確認 | Vercel 自動部署；技術發布者確認 | Vercel Dashboard、瀏覽器 | Production 顯示 Ready，正式網址可開啟 |
| 10 | 正式內容驗收及結案 | 秘書長、技術發布者 | 正式網站、發布紀錄 | 正式驗收完成並留存紀錄 |

以下是可直接交付各角色執行的詳細 SOP。任何一步未通過，都應停在該步驟修正，不得先上線再補核准。

### 5.2 步驟 1：製作內容並匯出上架包

**負責角色：** 秘書長<br>
**協助角色：** 內容提供者；重大內容由會長或授權主管先確認<br>
**操作介面：** CTDF 後台 `https://ctdf-web.vercel.app/admin/login/`、瀏覽器、檔案總管

開始前應取得：完整文字、日期、分類、圖片、附件、來源、授權狀態、希望發布時間及需要的主管核准。

操作步驟：

1. 使用授權帳號登入 CTDF 後台。
2. 從左側選單進入「公告」、「賽事」、「影音」、「文件」或「頁面」。
3. 新增內容時按右上角「新增」；修改內容時，在原內容右側按「編輯」。
4. 填寫標題、分類、日期、摘要、內文及該內容類型的必要欄位。
5. 選取圖片或附件，確認檔名、版本與預定公開的檔案一致。
6. 按「儲存草稿」，確認畫面出現草稿已保存的訊息。
7. 按「預覽」，逐項檢查標題、日期、文字、連結、附件說明與排版。
8. 按「送交審核」。需要主管核准時，在取得核准前不要進行下一個動作。
9. 所有內容確認無誤後，按「核准並匯出 ZIP」。
10. 在電腦的「下載」資料夾找到 ZIP，另存為容易辨識的名稱，例如 `20261031_公告_代表隊選拔_v1.zip`。
11. 將 ZIP、希望發布時間、核准人及特殊注意事項交給技術發布者。

完成判定：技術發布者已收到可開啟的 ZIP，以及明確的內容核准與發布需求。

不得進行：不要把後台的「已核准匯出」或「已發布」狀態當成正式網站已經上線；不要把 GitHub 或 Vercel 密碼交給內容人員。

### 5.3 步驟 2：技術檢查、建立內容分支及提交

**負責角色：** 副秘書長／技術發布者<br>
**操作介面：** Windows 檔案總管、文字或程式編輯器、GitHub Desktop、本機測試網站

操作步驟：

1. 將收到的 ZIP 保存至本次發布工作資料夾，保留原始檔不覆寫。
2. 解壓 ZIP，檢查 `manifest.json`、`content/`、`uploads/` 與 `README.txt` 是否存在。
3. 確認標題、內容類型、附件清單、核准狀態與秘書長交付資訊一致；不一致時立即停止並退回。
4. 開啟 GitHub Desktop，確認目前 repository 是 `ctdf-web`。
5. 按 `Current Branch` 選擇 `main`，再按 `Fetch origin`；若畫面顯示 `Pull origin`，先按下以取得最新正式版本。
6. 按 `Current Branch` → `New Branch`。
7. 分支名稱輸入 `content/YYYYMMDD-short-title`，並確認基礎分支為 `main`，按 `Create Branch`。
8. 使用編輯器依 ZIP 更新對應網站檔案、圖片及附件。只處理本次核准的範圍。
9. 啟動本機測試網站，檢查首頁、列表、詳細頁、圖片、下載及手機畫面。
10. 回到 GitHub Desktop 的 `Changes`，確認沒有 `.codex/`、密碼、內部資料或與本次無關的檔案。
11. 在 `Summary` 輸入清楚的提交訊息，例如 `Publish representative team announcement`。
12. 按 `Commit to content/...`。
13. 按 `Publish branch`；分支已存在時按 `Push origin`。
14. 在 `History` 找到本次 commit，記錄其識別碼供後續核准比對。

完成判定：GitHub 上已存在內容分支，且本次 commit 可被其他人查看。

不得進行：不得直接在 `main` 修改或提交；不得使用 Force Push 覆寫已交付 Review 的版本。

### 5.4 步驟 3：部署至 Demo 環境

**負責角色：** 副秘書長／技術發布者<br>
**操作介面：** GitHub 網頁、Vercel Dashboard、瀏覽器

前置條件：Vercel Demo 專案已連接此 GitHub repository，並設定由 `demo` 分支部署固定 Demo 網址。

操作步驟：

1. 開啟 GitHub repository，進入 `Pull requests`。
2. 按 `New pull request`，將 `base` 選為 `demo`，`compare` 選為本次 `content/...` 分支。
3. 確認 `Files changed` 只有本次核准內容。
4. PR 標題填寫「Demo：內容類型－標題」。
5. PR 說明填入 ZIP 名稱、內容提供者、核准者、希望發布時間、測試結果及回復方式。
6. 按 `Create pull request`。
7. 等待 GitHub／Vercel 檢查完成；有失敗項目時先查看原因，不得直接忽略。
8. 檢查無誤後，將 PR 合併至 `demo`。合併時不要刪除內容分支，正式發布還會使用。
9. 開啟 Vercel Dashboard → Demo 專案 → `Deployments`。
10. 找到來源為 `demo` 且包含本次變更的部署，等待狀態變成 `Ready`。
11. 開啟固定 Demo 網址，強制重新整理，確認新內容已出現。
12. 將 Demo 網址、內容頁路徑、Demo PR 及 commit 交給秘書長。

完成判定：固定 Demo 網址已顯示本次版本，且 Vercel 部署狀態為 `Ready`。

不得進行：不得在此步驟建立或合併至 `main` 的 PR；Vercel 部署失敗時不得聲稱已可 Review。

### 5.5 步驟 4：Demo 上板 Review

**主要負責角色：** 秘書長<br>
**共同 Review：** 內容提供者；重大或敏感內容加入會長／授權主管<br>
**操作介面：** 電腦與手機瀏覽器、Demo 網站、本手冊第 9 節檢核表

操作步驟：

1. 確認網址是 Demo，不是 `ctdf.org.tw` 正式網站。
2. 先從 Demo 首頁依一般使用者路徑進入內容，不只開啟技術人員提供的直接網址。
3. 檢查首頁入口、列表排序、標題、分類、日期、摘要及詳細內容。
4. 開啟每個圖片、附件、報名網址及影音連結。
5. 使用手機再次檢查文字、按鈕、圖片與橫向捲動。
6. 修改內容時，與目前正式網站逐項比較；下架時，確認公開入口及附件處理方式符合申請。
7. 檢查是否有內部備註、測試文字、個資或未授權素材。
8. 將每個問題記為「頁面網址、位置、目前內容、應改內容」，不要只寫「請修改」。
9. Review 結果選擇「通過」或「退回修正」，並回覆技術發布者。

完成判定：已有明確的通過結果，或可執行的完整修正清單。

不得進行：Demo Review 通過不等於正式發布核准；尚有問題時不得要求先上正式網站再修正。

### 5.6 步驟 5：修正並重新 Review

**負責角色：** 秘書長負責內容決定；副秘書長／技術發布者負責網站修正<br>
**操作介面：** CTDF 後台、GitHub Desktop、GitHub 網頁、Vercel Dashboard、Demo 網站

沒有任何問題時：秘書長註明「Demo Review 無需修正」，直接進入步驟 6。

有問題時的操作步驟：

1. 秘書長整理單一版本的修正清單；涉及內容事實時，先向內容提供者確認正確文字。
2. 若需重新產生內容包，秘書長在後台修改、預覽、重新核准並匯出新版 ZIP，版本改為 `v2`、`v3` 等。
3. 技術發布者切換回原 `content/...` 分支，不建立另一個同名內容分支。
4. 依修正清單更新網站並完成本機測試。
5. 在 GitHub Desktop 建立新的 commit，按 `Push origin`。不要修改或覆寫先前已推送的 commit。
6. 在 GitHub 建立新的 `content/...` → `demo` PR，或依專案規則更新 Demo 分支。
7. 等待 Vercel Demo 部署狀態為 `Ready`。
8. 技術發布者把新的 commit 與 Demo 網址交給秘書長。
9. 秘書長重新執行步驟 4；不得只檢查被修改的一行，也要確認相鄰內容未受影響。
10. 重複此流程，直到 Demo Review 通過。

完成判定：秘書長確認 Demo 無待修項目，並記錄最後通過的 commit。

### 5.7 步驟 6：核准發布正式版

**負責角色：** 秘書長<br>
**必要加簽：** 重大聲明、政策、爭議、個資、青少年或敏感內容由會長／授權主管加簽<br>
**操作介面：** Email、Demo PR 留言或總會使用的簽核紀錄

操作步驟：

1. 取得技術發布者提供的 Demo 網址與最後 commit。
2. 確認第 9 節檢核表全部完成，且沒有未解決問題。
3. 以可留存方式寫下以下資料：

```text
內容標題：
Demo 網址：
核准 commit：
核准人：
核准日期時間：
核准結果：同意發布正式版
指定發布時間：立即／指定日期時間
備註：
```

4. 將核准紀錄傳給技術發布者；使用 GitHub 時，可貼在 Demo PR 留言中。
5. 指定時間發布時，清楚註明台灣時間與日期。

完成判定：技術發布者已收到包含 commit 的「同意發布正式版」紀錄。

不得進行：口頭同意、通訊軟體單一貼圖或「看起來可以」不視為正式核准。

### 5.8 步驟 7：建立正式版 Pull Request

**負責角色：** 副秘書長／技術發布者<br>
**操作介面：** GitHub 網頁

操作步驟：

1. 開啟 GitHub repository → `Pull requests` → `New pull request`。
2. `base` 選擇 `main`，`compare` 選擇已通過 Demo Review 的 `content/...` 分支。
3. 進入 `Commits`，確認包含秘書長核准的 commit。
4. 進入 `Files changed`，確認沒有 Demo 專用設定、未核准內容或其他發布項目。
5. PR 標題輸入「正式發布：內容類型－標題」。
6. PR 說明填入 Demo 網址、Demo PR、核准 commit、核准人、核准時間、ZIP 名稱、測試結果及回復方式。
7. 指定 Review 人員；若目前只有兩人，至少由秘書長確認 PR 說明中的核准資料無誤。
8. 按 `Create pull request`，等待檢查完成。

完成判定：已建立以 `main` 為 base 的正式 PR，內容及核准資料完整。

不得進行：若正式 PR 出現核准 commit 之後的新變更，必須退回 Demo 重新 Review。

### 5.9 步驟 8：比對核准版本並合併

**負責角色：** 副秘書長／技術發布者<br>
**建議覆核角色：** 第二位具 GitHub 權限的技術管理者<br>
**操作介面：** GitHub 網頁

操作步驟：

1. 開啟正式 PR，確認 `base: main`、`compare: content/...`。
2. 確認所有檢查為通過狀態，且沒有 merge conflict。
3. 在 `Commits` 比對秘書長核准的 commit。
4. 在 `Files changed` 再檢查一次圖片、附件、路徑與刪除檔案。
5. 確認 PR 在核准後沒有新增 commit；若有，停止合併並回到步驟 3 至 6。
6. 選擇 `Create a merge commit`／`Merge pull request`，以保留內容分支的核准 commit 供追溯。
7. 按 `Confirm merge`。
8. 暫時不要刪除內容分支，等步驟 10 正式驗收完成後再刪除。
9. 記錄正式 PR 編號及合併後的 `main` commit。

完成判定：正式 PR 顯示 `Merged`，變更已進入 `main`。

不得進行：檢查失敗、版本不符、未取得正式核准或有衝突時不得強行合併。

### 5.10 步驟 9：正式部署及技術確認

**自動執行：** Vercel Git 整合<br>
**負責確認角色：** 副秘書長／技術發布者<br>
**操作介面：** Vercel Dashboard、瀏覽器

操作步驟：

1. 合併 `main` 後，開啟 Vercel Dashboard →正式 Production 專案 → `Deployments`。
2. 找到來源分支為 `main`、commit 與正式 PR 相符的最新部署。
3. 等待狀態由 `Queued`／`Building` 變成 `Ready`。
4. 若部署顯示 `Error`，開啟該部署的 Build Logs，記錄錯誤並停止發布通知；不要把失敗部署當成完成。
5. 部署為 `Ready` 後，確認該部署已指向正式 Production domain。
6. 正式網域啟用前，開啟 `https://ctdf-web-production.vercel.app/`；正式上線後改開啟 `https://ctdf.org.tw/`，並強制重新整理。
7. 檢查首頁、內容頁、圖片、附件下載、外部連結及基本手機畫面。
8. 將正式網址、部署時間、正式 PR 與 production commit 交給秘書長驗收。

完成判定：Vercel Production 為 `Ready`，正式網域可開啟且技術檢查通過。

注意：`ctdf-web-production-<識別碼>-<帳號>.vercel.app` 是單次部署網址，可能需要 Vercel 登入且每次部署都可能改變；發布手冊與驗收紀錄應優先使用固定的 `https://ctdf-web-production.vercel.app/`，單次部署網址僅用於技術追蹤。

不得進行：不要只看 Vercel 顯示 Ready 就結案；必須實際開啟正式網域。

### 5.11 步驟 10：正式內容驗收及結案

**內容驗收角色：** 秘書長<br>
**技術結案角色：** 副秘書長／技術發布者<br>
**操作介面：** 正式網站、手機與電腦瀏覽器、GitHub PR、發布紀錄

秘書長操作步驟：

1. 正式網域啟用前，確認網址是 `https://ctdf-web-production.vercel.app/`；正式上線後確認網址是 `https://ctdf.org.tw/`。
2. 從首頁依一般使用者路徑進入本次內容。
3. 對照已核准的 Demo，檢查標題、日期、內文、圖片、附件及連結。
4. 使用手機再檢查主要畫面。
5. 回覆「正式內容驗收通過」，或立即列出錯誤及影響程度。

技術發布者操作步驟：

1. 確認正式 Production commit 與核准版本可追溯對應。
2. 填寫發布紀錄：內容標題、Demo 網址、核准人、核准 commit、正式 PR、Production commit、正式網址及完成時間。
3. 將 ZIP、核准紀錄及發布紀錄保存於總會指定位置。
4. 正式驗收通過後，才可刪除 GitHub 內容分支。
5. 若正式內容有誤，依第 11 節判斷建立修正 PR 或回復上一個正常版本。

完成判定：秘書長與技術發布者都已確認，發布紀錄完整，本次工作才可標記為完成。

## 6. 各角色操作步驟

### 6.1 內容提供者／業務承辦

1. 準備標題、摘要、完整內文、發布日期及下架或失效日期。
2. 提供原始附件，不以通訊軟體截圖取代正式文件。
3. 賽事資料須確認賽名、硬式／電子飛鏢、起訖日期、場館、地址、報名網址與規程版本。
4. 影音資料須提供正式來源網址，並確認圖片、影片與人物影像可公開使用。
5. 文件須註明版本號，以及是否取代既有文件。
6. 以可留存的方式交付秘書長，並回覆內容正確性確認。

### 6.2 秘書長：建立、修改與核准內容

1. 開啟 `https://ctdf-web.vercel.app/admin/login/` 並登入。
2. 從左側選單選擇「公告」、「賽事」、「影音」、「文件」或「頁面」。
3. 新增內容時按右上角「新增」；修改內容時在列表按「編輯」。
4. 依欄位輸入資料並選擇正確分類。
5. 加入圖片或附件後，確認檔名可辨識且不是舊版本。
6. 按「儲存草稿」。草稿只保存在目前瀏覽器，尚未送出或發布。
7. 按「預覽」，檢查標題、摘要、內文、日期、換行與手機閱讀效果。
8. 完成自我檢查後按「送交審核」。
9. 依內容性質取得必要的業務或主管核准。
10. 再次開啟內容，確認沒有待修事項後按「核准並匯出 ZIP」。
11. 保存 ZIP，不要重新解壓後再任意壓縮，以免匯入格式失效。
12. 將 ZIP、發布時間、核准者及特殊注意事項交給技術發布者。
13. 收到固定 Demo 網址後，以本手冊第 9 節檢核表進行上板 Review。
14. 確認 Demo 的首頁、列表、詳細頁、圖片、附件及手機版。
15. 明確回覆「同意發布正式版」或列出需修正項目；未回覆不視為同意。
16. 正式部署後再次開啟正式網址，完成正式環境驗收。

### 6.3 會長或授權主管：重大內容核准

1. 確認內容是否代表總會正式立場。
2. 檢查人名、組織名稱、政策、法律或爭議性敘述。
3. 確認涉及青少年、個資、照片或影音時已有適當授權。
4. 以 Email、簽核文件或其他可追溯方式回覆核准或退回修正。
5. 原則上不直接操作後台、GitHub 或 Vercel。

### 6.4 副秘書長／技術發布者：整合與發布

1. 接收 ZIP 後，確認檔名、交付人、核准人及預計發布時間。
2. 解壓檢查 `manifest.json`、`content/`、`uploads/` 與 `README.txt`。
3. 確認內容狀態為已核准，附件清單與實際檔案一致。
4. 若資料不完整、內容未核准或附件可疑，停止處理並退回秘書長。
5. 從最新 `main` 建立獨立內容分支，建議命名為 `content/YYYYMMDD-short-title`。
6. 依 ZIP 內容更新對應前台頁面與素材，不改動核准內容的事實與語意。
7. 在本機檢查頁面、連結、圖片、附件下載與手機版顯示。
8. 提交變更並推送內容分支，完成技術檢查或建立對 `demo` 的 Pull Request。
9. 在 PR 說明填入內容類型、上架原因、核准者、ZIP 編號、測試結果與回復方式。
10. 將內容合併至 `demo`，確認 Vercel Demo 部署成功。
11. 將固定 Demo 網址、內容路徑及版本 commit 交給秘書長 Review。
12. 若 Review 要求修改，在原內容分支修正並重新部署 Demo，不得直接進入正式環境。
13. 收到明確的「同意發布正式版」後，以同一內容分支對 `main` 建立正式 Pull Request。
14. 比對正式 PR 的 commit 與 Demo 核准版本；有差異時停止發布並重新 Review。
15. 合併至 `main`，等待 Vercel Production 部署完成。
16. 檢查正式首頁、內容頁、圖片、附件、外部連結與手機版。
17. 將 Demo 核准紀錄、正式網址、PR、Git commit 與完成時間回覆秘書長。

## 7. 修改已上架內容

修改錯字、日期、附件、圖片或網址，仍須走完整流程：

1. 內容提供者說明原內容網址、錯誤位置、正確內容與修改原因。
2. 秘書長在後台開啟原內容，修改後另存草稿並重新預覽。
3. 秘書長重新送審、核准並匯出新的 ZIP。
4. 技術發布者以新分支及新 PR 修改，不直接覆寫 `main`。
5. Demo 上板 Review 時同時比較修改前後內容。
6. Demo 通過後才發布正式版，並確認舊內容已被正確取代，附件不得仍指向舊版。

小錯字也應留下 GitHub 紀錄；不得為了省略流程直接在線上手動修改。

## 8. 下架流程

### 8.1 下架類型

| 類型 | 適用情況 | 處理原則 |
|---|---|---|
| 到期下架 | 報名截止、活動結束、暫時性公告失效 | 可改為封存，必要時保留歷史頁面 |
| 版本取代 | 新規程、新表單或新政策取代舊版 | 新版先上架，確認正常後再移除舊版入口 |
| 一般下架 | 內容不再適用但無立即風險 | 先於 Demo Review，再依正式發布流程處理 |
| 緊急下架 | 個資外洩、錯誤重大、未授權影像、法律或資安風險 | 先降低公開風險，再補齊紀錄與正式 PR |

### 8.2 下架申請資料

目前 Demo 尚無一鍵下架按鈕。秘書長應提供以下資料給技術發布者：

```text
下架內容標題：
正式網站網址：
內容類型：公告／賽事／影音／文件／頁面
處理方式：移除入口／封存／完全移除／以新版取代
下架原因：
希望生效時間：
替代內容或轉址網址：
申請人：
核准人：
```

### 8.3 一般下架操作

1. 秘書長確認下架原因、處理方式與是否保留歷史紀錄。
2. 重大內容下架先取得會長或授權主管同意。
3. 技術發布者建立 `content/YYYYMMDD-unpublish-short-title` 分支。
4. 依核准內容移除首頁入口、列表項目、附件或內容頁；需要保留歷史時改為封存呈現。
5. 先合併至 `demo` 並提供固定 Demo 網址。
6. 秘書長確認 Demo 中的內容已不再從公開入口存取，且替代連結正確。
7. 秘書長留下「同意正式下架」紀錄後，技術發布者才可將同一版本合併至 `main`。
8. 正式部署後再次確認正式網站及附件狀態。
9. 記錄 Demo 核准、正式下架時間、原因、PR、commit 與處理人員。

### 8.4 緊急下架操作

1. 發現個資、未授權素材、重大錯誤或資安風險者，立即通知秘書長與技術發布者。
2. 秘書長以可留存方式確認「緊急下架」，並指定需移除的網址與檔案。
3. 技術發布者使用最小範圍變更移除公開入口與敏感檔案，完成快速部署。
4. 正式網站確認風險解除後，再建立或補完 PR、核准紀錄及事件說明。
5. 若敏感檔案曾提交至公開 GitHub，僅刪除目前檔案可能不足，須另行評估 Git 歷史、快取與外部備份清除。
6. 事後確認原因、影響範圍、是否需要通知當事人，以及預防措施。

- [ ] 首頁及相關列表可到達新內容。
- [ ] 舊版內容或附件已依決定保留、封存或移除。
- [ ] PR、commit、發布時間與正式網址已記錄。

## 10. ZIP、草稿與檔案管理

### 10.1 ZIP 上架包內容

```text
manifest.json
content/<module>/<content-id>.json
uploads/<files>
README.txt
```

### 10.2 保存原則

- 草稿只存在建立草稿的瀏覽器，不會跨電腦同步。
- 不要清除該網站的瀏覽器資料，否則草稿可能遺失。
- 重要內容完成一個可審版本時，應匯出 ZIP 備份。
- ZIP 建議依 `YYYYMMDD_內容類型_標題_版本.zip` 另行保存。
- 核准紀錄、ZIP 與 PR 應能互相對照。
- 後台的「已發布」狀態只是 Demo 紀錄；是否真的上線，必須以正式網站及 GitHub 部署結果為準。

## 11. 異常與回復

### Demo 上板 Review 有誤

不要合併至 `main`。由技術發布者修正同一內容分支，重新部署 Demo，再由秘書長驗收。

### 正式部署後有誤

1. 技術發布者先判斷能否以新 PR 快速修正。
2. 影響重大時，回復到上一個已確認正常的 Git 版本。
3. 回復後確認首頁、內容頁與附件。
4. 秘書長重新提供正確內容，再走一次完整流程。

### 草稿遺失

1. 先確認是否使用了不同瀏覽器、不同電腦或無痕模式。
2. 使用先前匯出的 ZIP，從對應模組選擇「匯入 ZIP」。
3. 匯入後一律以草稿狀態重新檢查，不直接視為已核准。

### ZIP 無法匯入

- 僅匯入由本後台產生的 ZIP。
- 不要用其他壓縮工具重新壓縮或改變資料夾階層。
- 原 ZIP 仍無法匯入時，由技術發布者檢查 `manifest.json` 與檔案完整性。

## 12. 發布紀錄建議欄位

每次上架、修改或下架至少記錄：

| 欄位 | 說明 |
|---|---|
| 申請日期 | 收到內容或下架申請的日期 |
| 內容標題及類型 | 公告、賽事、影音、文件或頁面 |
| 動作 | 新增、修改、封存、下架、緊急修正 |
| 內容提供者 | 原始資料負責人 |
| 核准者及核准日期 | 秘書長及必要的主管核准 |
| ZIP／上架編號 | 對照匯出上架包 |
| GitHub PR／commit | 技術版本紀錄 |
| Demo 網址及核准紀錄 | 固定審閱網址、核准人與核准時間 |
| 核准 commit | 確保正式發布與 Demo Review 為同一版本 |
| 正式網址 | 發布後網址 |
| 發布／下架時間 | 實際生效時間 |
| 驗收人 | 正式網站確認人員 |

## 13. 現階段限制與下一版建議

目前 Demo 適合展示及小量人工發布，不等同正式 CMS。正式版建議增加：

- 個人帳號、多因素驗證與角色權限。
- 資料庫內容版本與跨裝置同步。
- 系統內審核、退回原因與電子簽核紀錄。
- 預定發布、預定下架與封存按鈕。
- 後台直接產生 Preview，但仍由授權人員核准正式發布。
- 完整操作紀錄、異常通知、備份與還原。
- 圖片及附件的病毒掃描、檔案限制與授權欄位。

在上述功能完成前，應以本手冊的雙人覆核、ZIP 交付、Pull Request、固定 Demo 上板 Review 與正式網站驗收作為發布控制。
